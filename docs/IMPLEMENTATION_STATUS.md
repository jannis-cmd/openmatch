# Implementation status

This repository is a verified pre-alpha development foundation, not a deployable dating service. The narrow local-demo scope is complete enough to extend without replacing its architecture.

| No universal demo credential | Demo-session issuance is opt-in; each client gets a random 256-bit bearer token, the API retains only its SHA-256 hash in memory for at most 12 hours by default, concurrent client requests share one bootstrap, and clients renew once after expiry/restart. All tokens still reach one shared demo identity, so this is explicitly not authentication or user isolation |
| Minimal isolated accounts | Web and production mobile clients can create an email/passphrase account, sign in, confirm inbox access through provider-neutral SMTP, inspect active sessions, revoke another session, change a passphrase after re-entering the current one, create and use one-time offline recovery codes, revoke the current session by signing out, and synchronously delete credentials, confirmation/recovery-code hashes, notification-address state, every session, and isolated application data. New and changed passphrases follow the NIST single-factor 15–128 character range, accept spaces/Unicode without composition or periodic-change rules, and reject a disclosed local common-value blocklist. A successful change atomically rotates the credential salt/hash and session token while revoking every previous session; native clients persist the replacement fail-closed. Recovery codes are eight independent 128-bit values shown only once and persisted only as SHA-256 hashes; generating a set requires the current passphrase and invalidates an older set, while successful recovery invalidates the complete set and atomically replaces the passphrase and all sessions. Primary and optional backup email confirmation codes are random eight-digit values sent only through explicitly configured TLS-required SMTP, expire within 24 hours, are stored as random-salted scrypt hashes, are single-use, preserve failed attempts across same-address resend, and never enter an API response or log. Adding, replacing, or removing a backup address requires current-passphrase reauthentication; the backup address cannot sign in, recover the account, affect matching, prove identity, or act as MFA. Confirmed accounts receive sparse provider-backed notices after passphrase changes, replacement recovery codes, account recovery, or backup-address changes; delivery is attempted at every confirmed inbox with no secret, link, IP, or device detail, and all clients disclose complete/partial/failed/unconfigured/unverified delivery. Failed or partial operation responses immediately produce a conservative persistent retry warning even if the exact queue-status request also fails; web and native poll only while a queue is pending and the client is active, prevent concurrent manual retries, and preserve the warning when a retry request fails. When primary delivery is configured, unconfirmed accounts cannot opt into or appear in account matching; confirmation proves inbox access, not identity or MFA. The session list exposes only a broad allowlisted client type, creation/expiry times, and current status—not IP, device fingerprint, exact model, user agent, or activity history. Email is normalized, passphrases are stored only as per-account salted scrypt hashes, raw 256-bit session tokens are returned once while only SHA-256 hashes persist server-side, authentication and credential-change/recovery/confirmation endpoints share a separate conservative throttle, and every protected operation is routed to an account-specific SQLite store. iOS/Android restore account sessions from device-only, unlocked-device Expo SecureStore, remove them on sign-out/deletion/expiry, and fail closed on unavailable or malformed secure state. Tests prove accounts cannot read one another's private preferences, non-mutual connections, or sessions; the separate directory consent deliberately authorizes eligible public-profile disclosure. Passkeys, a staffed repudiation path, multi-host notification delivery with bounce/complaint handling, a production breach-password service/local corpus, production migration tooling, and security review remain required before a pilot |
| Non-production account-to-account flow | Completed, active accounts with a separate versioned and reversible account-matching opt-in whose normalized self-entered city/region text matches exactly can become candidates for one another. Enabling declares availability for 30 days; web, iOS, and Android show the exact expiry and require explicit renewal. Expiry excludes the person both as viewer and candidate without deleting connections, recording login/activity history, or publishing a last-active time. The duration is a testable prototype hypothesis, not a validated optimum. Existing, opted-out, and legacy-consent accounts remain excluded until an explicit current declaration. The shared deterministic kernel applies both people's boundaries and priorities; candidate-side traces remain private. One-sided interest remains private, mutual interest creates the same connection in both isolated stores, messages are delivered to both stores, and unmatch/block/polite-close close the reciprocal connection. Cross-account actions are first persisted in a minimal delivery journal, replay in order after interruption, and commit an opaque event ID with each target mutation so retry is idempotent; completed payloads are immediately removed. Failed attempts retain only bounded operational metadata; web, iOS, and Android immediately replace generic failure handling with an explicit safely-queued warning, refresh the affected account's pending status, and never claim the other person received it. Pending actions are not automatically discarded. Clients retain an account-scoped random request ID while retrying an unchanged message draft and preserve the exact pending pair across a browser reload or native process restart—per-tab on web and in device-only protected storage on mobile. Successful delivery, editing, closure, sign-out, account replacement, deletion, or session rejection removes it. The API returns the original message after a lost response and rejects request-ID reuse for different content. Clients disclose that region matching is exact text equality—not geocoding or a distance estimate—and expose withdrawal from Profile. Automated coverage exercises consent and expiry exclusion, reciprocal introduction → mutual connection → message → unmatch, interrupted client send → reload → same-ID retry, repeated API requests, conflicting request-ID reuse, plus a simulated interruption between target writes and exactly-once visible server recovery after restart. This remains a non-production bridge without a distributed worker, staffed retry/dead-letter workflow, viable location, identity, or moderation design |

## Deliberately not claimed

Before any real-user pilot, the project still requires a deployed HTTPS service, verified production authentication and authorization, a transactional multi-user datastore and migrations, privacy-reviewed coarse location, identity/inclusion research, photo storage and processing, staffed moderation and appeals, rate limiting beyond the local boundary, encryption and secret management, notification design, deletion/backup drills, device-level assistive-technology testing, security review, legal/DPIA review, and a geographically viable safety program.

The matching method is a transparent hypothesis. Passing tests proves implementation invariants, not that the score predicts attraction, love, relationship satisfaction, or safety. Those claims remain explicitly forbidden without prospective evidence.

## Best next development increment

Replace the exact free-text region bridge with privacy-reviewed coarse-region identifiers and measure whether mutually eligible people receive a viable, equitable opportunity set before any pilot. This requires a pilot-region decision and inclusion research; it must not silently become precise location tracking.

Continue the account lifecycle: passkeys, a staffed repudiation path, multi-host security-notification workers plus bounce/complaint handling, a transactional production datastore/migrations, staffed dead-letter handling and monitoring for both delivery outboxes, and independent security review. The current security-notice outbox durably retains failed recipients, avoids resending to successful recipients, retries in one process with bounded exponential backoff and a short lease, exposes pending state in every client, and supports authenticated manual retry without automatic discard. Validate active-session, confirmation, recovery, and interrupted delivery management in threat modeling and device-level accessibility testing. Do not add photos, engagement notifications, or broader matching fields until privacy, inclusion, and safety requirements for those features are resolved.
