# Implementation status

This repository is a verified pre-alpha development foundation, not a deployable dating service. The narrow local-demo scope is complete enough to extend without replacing its architecture.

## Implemented and verified

| Requirement | Evidence |
|---|---|
| Web, iOS, and Android clients | Next.js production build plus Expo iOS and Android exports |
| One durable product flow | Onboarding → finite introductions → decision → mutual connection → text message → safety action |
| Multiple conversation readiness | Web, iOS, and Android select an explicit connection instead of silently targeting the first API record; switching clears the previous draft/messages, loads only the selected conversation, and every send/mute/meeting/safety action uses that selected connection. Sent and received messages use opposing alignment, neutral color, visible author names, and one complete accessible “Author: message” label so authorship never depends on color alone |
| User-controlled public profile | Name, adult age, approximate city/region, optional free-text pronouns, relationship intention, and biography are editable during setup and later on web and mobile |
| User-controlled matching profile | Human-written prompt/answer, 1–5 selected values, smoking, children plans, and schedule are editable during setup and later on web/mobile; validation rejects missing, duplicate, oversized, or unknown states, and profile changes invalidate the current batch |
| Public meeting readiness | “Prefer to chat first” or “Ready to meet in person” is editable and visible on all clients, migrates existing profiles to the cautious default, and is explicitly excluded from matching |
| User-controlled mutual boundaries | Age range, accepted relationship intentions, smoking, children, and distance boundaries are editable independently from ordering priorities on web and mobile |
| Explicit prototype consent | Server-enforced adult confirmation and local data-use acknowledgement produce a timestamped, versioned receipt that is exported and cleared on deletion |
| Separate research consent | Optional research enrollment defaults to no receipt, can be opted into and withdrawn independently on web/mobile, never changes matching, and is versioned/exported/deleted |
| Transparent reciprocal matching | Shared deterministic kernel; mutual boundaries; separate A→B and B→A compatibility and weights; harmonic mean; versioned explanations |
| Reproducible exploration | Five-person batches reserve one visibly labeled slot selected from eligible profiles and positioned by a public UTC-week seed; the durable/exportable batch snapshot prevents redraws across actions or restarts, selection leaves scores unchanged, and the actual probability is recorded only after an explicit decision; smaller batches currently have no exploration slot |
| Matching invariant tests | 2,000 deterministic generated cases verify hard-boundary exclusion, two-sided symmetry, monotonicity, score bounds, bounded exposure, and zero-priority behavior alongside concrete adversarial cases |
| In-app transparency center | Deployed algorithm version, validated commit link (or explicit unpinned-development state), objective, source code, evidence register, decision history, privacy distinction, and known limitations are reachable on web and mobile |
| Logged-out public transparency | The landing page exposes source, evidence, decision history, data inventory, known limits, and the shared offline score calculator without account/demo entry or API traffic |
| Independently hostable public site | An unconfigured production build keeps all public content and the local calculator available, disables every demo entry point with an honest explanation, clears stale demo entry, and never falls back to the visitor's localhost; a configured hosted demo requires a plain HTTPS origin |
| Local score calculator | Web, iOS, and Android call the shared deterministic kernel with adjustable synthetic two-sided fit and boundary inputs; no API request is involved |
| Machine-readable data inventory | Every current local storage/export collection lists its fields, purpose, retention rule, access roles, disclosure, and notable exclusions in `docs/DATA_INVENTORY.json` |
| Proximity without public precision | Internal coarse-region estimate; only five public distance bands leave the matching boundary |
| Limited learning from decisions | Interested/Pass observations store only shown A-side factors and selection probability; suggestions require 20 mixed observations; no automatic changes |
| Saved introductions | Save/restore is persisted independently from Interested/Pass, available on web and mobile, private from candidates, exported, and cleared on reset/deletion; the prototype queue has no scheduled expiry yet |
| User-controlled finite delivery | A persisted 1–5 batch-size control is enforced by the API and exposed on web and mobile with an explicit hypothesis caveat; pause remains separately available |
| Honest batch completion | The API publishes the reproducible Monday `00:00 UTC` boundary; web/mobile show it without promising inventory, never recycle resolved profiles, expose no “start over” action, and state that only newly eligible profiles may appear |
| Personal-data transparency | JSON export, pause, hide, resume, and atomic synchronous deletion/reset from Profile on web and mobile; deletion returns a timestamped completion receipt only after every local collection and consent state is cleared, rolls back fully on storage failure, and does not retain the receipt server-side |
| Preference privacy | Candidate factor traces default private; sharing is explicit; redaction is tested not to change scores |
| Basic safety | Report/block from introductions and conversations, mutual-only user-written text messaging, no read receipts, confirmed destructive actions, categorized reports with optional user context, private report history/status, visible report receipts, and always-reachable safer-dating/scam guidance |
| Contextual scam friction | Two published deterministic rules detect external links and common payment-request wording locally before send and again at the API boundary; web/mobile explain the exact warning and false-positive risk, require explicit “send anyway,” retain no separate risk label, and never report, block, or alter visibility/matching automatically |
| No-report support path | The public landing page, signed-in web app, iOS, and Android expose current Swiss police (117), medical emergency (144), and independent victim-support (142/site) resources without requiring an OpenMatch report; copy distinguishes emergency from counselling, scopes numbers geographically, and warns about external/device records |
| Polite conversation close | Web and mobile can atomically send a published standard closing message and close the connection; the final message remains in export while silence and unmatching remain unpenalized alternatives |
| Private conversation mute | Web and mobile persist mute independently from unmatch/block/report, export it, and explain that it will suppress future message notifications while the current prototype sends none |
| Private meeting-planning preference | After mutual interest, web and mobile offer reversible “Not yet” and “Open to planning” states with public-place safety guidance; the state is exported/deleted, never affects matching, requests no location, is not sent to the demo candidate, and is explicitly not treated as evidence that a date occurred |
| Human-controlled conversation starter | Web and mobile can copy a deterministic draft based only on the candidate’s visible, human-written prompt answer; the person must review/edit and explicitly send it |
| Local API hardening | SQLite, validation, 64 KiB body limit, allowlisted browser origins, no-store responses, configurable per-address request throttling with `Retry-After`, known-profile checks, explicit demo boundary |
| No universal demo credential | Demo-session issuance is opt-in; each client gets a random 256-bit bearer token, the API retains only its SHA-256 hash in memory for at most 12 hours by default, concurrent client requests share one bootstrap, and clients renew once after expiry/restart. All tokens still reach one shared demo identity, so this is explicitly not authentication or user isolation |
| Minimal isolated accounts | Web and production mobile clients can create an email/passphrase account, sign in, confirm inbox access through provider-neutral SMTP, inspect active sessions, revoke another session, change a passphrase after re-entering the current one, create and use one-time offline recovery codes, revoke the current session by signing out, and synchronously delete credentials, confirmation/recovery-code hashes, every session, and isolated application data. New and changed passphrases follow the NIST single-factor 15–128 character range, accept spaces/Unicode without composition or periodic-change rules, and reject a disclosed local common-value blocklist. A successful change atomically rotates the credential salt/hash and session token while revoking every previous session; native clients persist the replacement fail-closed. Recovery codes are eight independent 128-bit values shown only once and persisted only as SHA-256 hashes; generating a set requires the current passphrase and invalidates an older set, while successful recovery invalidates the complete set and atomically replaces the passphrase and all sessions. Email confirmation codes are random eight-digit values sent only through explicitly configured TLS-required SMTP, expire within 24 hours, are stored as random-salted scrypt hashes, are single-use, preserve failed attempts across one-minute-limited resend, and never enter an API response or log. When delivery is configured, unconfirmed accounts cannot opt into or appear in account matching; confirmation proves inbox access, not identity or MFA. Confirmed accounts receive sparse provider-backed notices after passphrase changes, replacement recovery codes, and account recovery; no secret, link, IP, or device detail enters a notice, and all clients disclose sent/failed/unconfigured/unverified delivery. The session list exposes only a broad allowlisted client type, creation/expiry times, and current status—not IP, device fingerprint, exact model, user agent, or activity history. Email is normalized, passphrases are stored only as per-account salted scrypt hashes, raw 256-bit session tokens are returned once while only SHA-256 hashes persist server-side, authentication and credential-change/recovery/confirmation endpoints share a separate conservative throttle, and every protected operation is routed to an account-specific SQLite store. iOS/Android restore account sessions from device-only, unlocked-device Expo SecureStore, remove them on sign-out/deletion/expiry, and fail closed on unavailable or malformed secure state. Tests prove accounts cannot read one another's private preferences, non-mutual connections, or sessions; the separate directory consent deliberately authorizes eligible public-profile disclosure. Passkeys, a second notification address, a staffed repudiation path, durable notification retry/monitoring, a production breach-password service/local corpus, production migration tooling, and security review remain required before a pilot |
| Non-production account-to-account flow | Completed, active accounts with a separate versioned and reversible account-matching opt-in whose normalized self-entered city/region text matches exactly can become candidates for one another. Existing and opted-out accounts remain excluded. The shared deterministic kernel applies both people's boundaries and priorities; candidate-side traces remain private. One-sided interest remains private, mutual interest creates the same connection in both isolated stores, messages are delivered to both stores, and unmatch/block/polite-close close the reciprocal connection. Web, iOS, and Android disclose that this is exact text-region matching—not geocoding or a distance estimate—and expose withdrawal from Profile. Automated integration coverage exercises consent exclusion, reciprocal introduction → mutual connection → message → unmatch. This is a non-production bridge, not a viable location, identity, moderation, or distributed-transaction design |
| Fail-closed mobile configuration | No private network address is committed to an EAS profile; each cloud environment must supply a plain HTTPS API origin, a pre-install hook rejects unsafe builds, and runtime validation makes configuration failure visible without attempting a request |
| Accessibility baseline | Semantic controls, visible/non-color states, automated WCAG 2.2 A/AA scans at four web states, native component queries, contrast fixes |
| Open development | AGPL software license, CC BY documentation license, governance, research proposal template, evidence register, decision log, and formatting gate |

## Deliberately not claimed

Before any real-user pilot, the project still requires a deployed HTTPS service, verified production authentication and authorization, a transactional multi-user datastore and migrations, privacy-reviewed coarse location, identity/inclusion research, photo storage and processing, staffed moderation and appeals, rate limiting beyond the local boundary, encryption and secret management, notification design, deletion/backup drills, device-level assistive-technology testing, security review, legal/DPIA review, and a geographically viable safety program.

The matching method is a transparent hypothesis. Passing tests proves implementation invariants, not that the score predicts attraction, love, relationship satisfaction, or safety. Those claims remain explicitly forbidden without prospective evidence.

## Best next development increment

Continue the account lifecycle: passkeys, a second notification address, a staffed repudiation path, durable notification retry plus bounce/complaint handling, a transactional production datastore/migrations, endpoint-specific abuse controls, and independent security review. Validate active-session, confirmation, and recovery management plus the non-production account-to-account flow in threat modeling and accessibility testing. Design privacy-reviewed coarse-region identifiers instead of relying on exact free-text equality, and test reciprocal opportunity before any pilot. Do not add photos, engagement notifications, or broader matching fields until privacy, inclusion, and safety requirements for those features are resolved.
